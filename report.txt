Summary of Findings:
- Critical (Logic/Memory): 3
- Warning (Potential Issues): 5

--------------------------------------------------------------------------------
1. CRITICAL ISSUES
--------------------------------------------------------------------------------
[C1] Splay Tree Implementation (splay_tree.c)
- Issue: Global 'splay_root' variable. 
- Impact: Prevents creating multiple instances of a Splay Tree. Not thread-safe. Standard library design patterns suggest passing the root/tree pointer to functions.

[C2] Memory Leak in B+ Tree Benchmark (benchmark_btree.c)
- Issue: Cleanup code for BPlusTree is commented out (Lines 130-131).
- Impact: For every test size and pattern, a B+ Tree structure is leaked. With 100,000 nodes and multiple runs, this consumes significant memory.

[C3] RB Tree Delete Logic (rb_tree.c)
- Issue: Missing NIL sentinel node handling.
- Impact: 'fixDelete' checks 'if(x)' but if 'x' is NULL (which happens for leaf deletions), the rebalancing loop might terminate prematurely or skip necessary color fixes. Line 215-217 checks 'if(x)', but the black-height property might still be violated if the fix-up doesn't proceed.

--------------------------------------------------------------------------------
2. WARNINGS (Potential Logic/Memory Issues)
--------------------------------------------------------------------------------
[W1] Resource Allocation Failure (General)
- Files: avl_tree.c, rb_tree.c, splay_tree.c, benchmark.c
- Issue: 'malloc' and 'calloc' return values are NOT checked for NULL.
- Impact: Programs will crash with SIGSEGV if memory is exhausted.

[W2] Incomplete Wrapper Cleanup (btree.c, bplustree.c)
- Issue: 'bt_free' and 'bp_free' only free the nodes. The 'BTree' and 'BPlusTree' wrapper structs (allocated in 'bt_create'/'bp_create') must be freed separately by the user.
- Impact: High risk of small memory leaks if users only call free on the root node.

[W3] Hardcoded Paths (benchmark.c)
- Issue: Line 34 contains an absolute path 'D:/Sem_4/ADS_CP/result/results.csv'.
- Impact: The code will fail to run on any environment where the directory structure or drive letter differs.

[W4] Ambiguous Duplicate Key Handling (Standard Trees)
- Issue: Insertion logic for B-Trees and BSTs doesn't always explicitly prevent or handle duplicate keys correctly for unique-set behavior.
- Impact: May lead to undefined behavior in search or deletion if duplicates are present but not handled.

--------------------------------------------------------------------------------
3. STYLE & DESIGN ISSUES
--------------------------------------------------------------------------------
[S1] Inconsistent API Design
- Observation: Some B-tree functions take 'BTree*' (insert, delete), while others take 'BtNode*' (search, get_height). This is inconsistent for the library user.

[S2] Dead Code/Comments
- Observation: benchmark_btree.c has large blocks of commented-out code (B+ delete section). This should be removed or moved to a 'feature/todo' branch.

[S3] Magic Numbers
- Observation: While BT_ORDER is defined, some split/merge arithmetic relies on constants that assume a specific order (e.g. median index 2).

[S4] Portability (benchmark.c)
- Observation: Use of 'system("if not exist ...")' is Windows-specific. Use of mkdir(path, mode) or similar would be more portable.

[S5] Global Metric Pollution
- Observation: Long long metrics (rotations, comparisons) are global. This makes it impossible to benchmark multiple tree instances in parallel or interleaved.
